# Verification plan

Upstream is pinned in `scripts/setup.sh` (`UPSTREAM_SHA`). Every result folder must record the SHA, hardware, dtype and the exact command it ran.

## Phase 0: Smoke test (CPU OK, ~15 min)

- `bash scripts/setup.sh && python scripts/smoke_test.py --device cpu`
- Pair: receiver `Qwen/Qwen3-0.6B`, sharer `Qwen/Qwen2.5-0.5B-Instruct`, fuser `qwen3_0.6b+qwen2.5_0.5b_Fuser`.
- Pass: C2C produces coherent output, and we have the latency for receiver-alone vs C2C.
- Note: cloud sandboxes may block Hugging Face downloads. If so, run this phase on a GPU box instead.

## Phase 1: Reproduce the accuracy claims (GPU required)

Run the upstream `script/evaluation/unified_evaluator.py` with `recipe/eval_recipe/unified_eval.yaml` for each mode:

| Mode | What it measures |
|---|---|
| receiver alone | baseline for C1 |
| sharer alone | sanity check |
| T2T (sharer writes text, receiver reads it) | baseline for C2 and C3 |
| C2C | the claim |

- Benchmarks: the ones the paper reports (MMLU-Redux, ARC-C, OpenBookQA, C-Eval). Start with the 0.6B+0.5B pair, then Qwen3-1.7B+Qwen2.5-1.5B.
- Use the same prompts, greedy decoding and seed for every mode.
- Report: accuracy ± 95% CI (bootstrap), using the paper's numbers as reference.
- Hardware: one 24 GB GPU (RTX 4090, L4 or A10) is enough for the small pairs. Options: RunPod, Modal, Colab Pro.

## Phase 2: Reproduce the latency claim (GPU required)

- Compare C2C vs T2T end to end (wall-clock per query, p50/p95), at batch size 1 and with warm-up.
- Record tokens generated by the sharer in T2T. Most of the latency gain should come from skipping that generation, so the speedup depends on how much text T2T produces.

## Phase 3: Fit for our environment

Only if Phases 1–2 hold up. Questions to answer:

1. Do we have, or want, local open-model sub-agents? If not, stop here: C2C doesn't apply to API models.
2. Fuser cost: training a fuser for a new model pair (`script/train/SFT_train.py`). Measure GPU-hours and data needs.
3. Generalization: does a fuser trained on general data help on *our* tasks (code, tool use, long context)? Upstream benchmarks are mostly multiple-choice QA.
4. Look at the follow-up [AKV](https://github.com/thu-nics/AKV) ("Cache Engineering for Agents"), which may target agent workflows more directly.

## Go/no-go

- **Go**: C1 and C2 reproduce within the CIs, C3 shows ≥1.5× speedup, and a concrete local-model use case exists in our stack.
- **No-go**: claims don't reproduce, or no part of our stack runs open models that we control.
