# Training-free improvements for the local coding helper

**Research checked:** 2026-11-04  
**Scope:** methods that can improve the Qwen3.6-35B-A3B helper without gradient training on our data. No model weights were downloaded, no code was changed, and no commit was made. Browsing was limited to CamoFox and primary sources, official code, and Hugging Face model metadata. Model search is a point-in-time, non-exhaustive check.

## Decision

There are two credible new interventions to pilot:

1. **Reuse a same-base coding checkpoint, then test a small task-vector merge only if a single checkpoint helps.** This has the strongest direct coding evidence and exact-base candidates. The direct checkpoint swap is much cheaper than a merge, but the merged full-precision source weights are large.
2. **Runtime residual-stream steering for spec fidelity and review-note adherence.** It targets two observed failure groups without editing or requantizing the model. The mechanism is plausible and light, but the steering literature does not establish code-generation gains.

Run the existing test-feedback path as a cheap baseline at the same time. The project already has it in **tools/autofix.py** and **tools/ft_eval.py --attempts**; this is a present feature to measure, rather than a new model intervention.

The first public-source check found **yes**, several code-oriented checkpoints declare Qwen3.6-35B-A3B as their base. The best evidenced full checkpoints are [Kwaipilot KAT-Coder](https://huggingface.co/Kwaipilot/KAT-Coder-V2.5-Dev) and [Alibaba Logics-SWE](https://huggingface.co/Logics-MLLM/Logics-SWE-Qwen3.6-35B-A3B). Their public configs share the local model’s architecture dimensions, 40-layer pattern, and vocabulary size. Their tokenizer metadata follows the Qwen3.6 tokenizer and special-token scheme. I did not compare every tokenizer file byte-for-byte or verify all source tensor hashes, so these are merge-compatible candidates pending revision and tensor checks, not a proof of identical file bytes.

## Data classes

These labels describe how a method avoids training on our data:

- **(a) No gradient updates at all.** May still compute a direction, edit weights analytically, or use an unlabeled calibration set.
- **(b) Small unlabeled calibration set.** Usually tens to hundreds of prompts used for activation or routing statistics. This is compatible with (a); it does not imply gradient training.
- **(c) Reuses weights someone else trained.** The original authors may have used gradients and private or public data; we do not repeat that training locally.
- **(d) Inference-time only.** Changes decoding, sampling, routing, or verification while leaving checkpoint weights unchanged.

For contrastive activation methods, the examples are tagged as preferred/unpreferred or positive/negative. That needs behavior labels and therefore does **not** satisfy the strict no-label definition of (b). It is still (a)+(d) with respect to our model’s weights.

Execution feedback is already implemented, so its rank reflects the incremental best-of-N extension rather than adopting it from zero. A method with published benchmark gains on a different model is evidence for a pilot, not a prediction for our 35B checkpoint.

## Merge mechanics, quantization, and memory

For a fine-tune with weights \(W_i\) and its common base \(W_0\), define \(\Delta_i = W_i - W_0\). The simplest combined model is:

\[
W_{\mathrm{merge}} = W_0 + \lambda_1\Delta_{\mathrm{KAT}} + \lambda_2\Delta_{\mathrm{Logics}}.
\]

Start with one candidate at a time. If both individual checkpoints help and updates interfere, compare simple task arithmetic with TIES; add DARE only if the delta distribution meets its small-update assumptions. Use SLERP only as an additional exploratory arm. **Do not** fit merge weights on the eight held-out tasks.

An MLX affine-4-bit tensor is not a normal dense floating-point tensor. The safe pipeline is:

1. Obtain the original same-revision BF16 base and the BF16 fine-tune checkpoint(s); verify tensor names, shapes, tokenizer, and source revision.
2. Compute deltas against the original BF16 base. The local q4 checkpoint alone is not sufficient to reconstruct the exact BF16 task vector.
3. Merge in floating point. A custom reader can stream or chunk by tensor, expert, or vocabulary row so the entire model is never resident. TIES/DARE must use the same aligned tensor values in each chunk and persist random seeds/masks.
4. Quantize the merged model back to the local q4 affine, group-size-64 format, keeping router/shared gates at the matching 8-bit settings where supported.
5. Compare the quantized result with both source checkpoints on logits and the frozen task suites. Small deltas may disappear; requantization may also change unrelated parameters.

**Mergekit is a useful implementation and reference, not proof of a low-memory MLX path.** Its documented methods operate on model tensors and the current docs do not claim native support for our MLX affine q4 shards or this exact hybrid MoE. Do not load the whole BF16 model twice into unified memory. Chunked arithmetic is feasible in principle, but the Qwen3.6 expert tensor layout and mergekit’s actual memory behavior must be tested on a small model first.

Approximate raw payload sizes, using the local config (2048 hidden size, 512 MoE intermediate size, 256 experts):

| Tensor scope | Elements | BF16 | FP32 |
|---|---:|---:|---:|
| One expert, one 2048×512 MLP projection | 1,048,576 | 2 MiB | 4 MiB |
| One expert, gate+up+down projections | 3,145,728 | 6 MiB | 12 MiB |
| All 256 experts, one such projection in one layer | 268,435,456 | 512 MiB | 1 GiB |
| All 256 experts, gate+up+down in one layer | 805,306,368 | 1.5 GiB | 3 GiB |
| Input embedding matrix, 248320×2048 | 508,559,360 | about 0.95 GiB | about 1.90 GiB |

These figures omit biases, quantization scales, attention, vision, metadata, allocator overhead, and the second source tensor. A 35B BF16 checkpoint is roughly 70 GB decimal. A single base + one fine-tune + BF16 output is about 210 GB of files; base + two fine-tunes + output is about 280 GB if all are materialized. Per-expert chunking reduces working memory dramatically: one projection can be held in a few MiB per source/accumulator rather than hundreds of MiB for the stacked expert tensor. The machine has 32 GB shared memory, not a dedicated 32 GB CPU RAM plus GPU pool; keep the MLX inference server stopped during conversion/merge and check free disk before the pilot.

## Runtime activation steering in MLX

CAA and related activation-addition work construct a direction from positive/negative residual-stream contrasts and add it at inference. The primary CAA source is [Panickssery et al.](https://arxiv.org/abs/2312.06681), with [official code](https://github.com/nrimsky/CAA). Related activation addition is [Turner et al.](https://arxiv.org/abs/2308.10248). [ITI](https://arxiv.org/abs/2306.03341) uses trained probes to identify truthfulness-related heads and intervenes at inference; its [code](https://github.com/likenneth/honest_llama) and TruthfulQA results are not code-generation evidence. Useful implementation references include [repeng](https://github.com/vgel/repeng), [steering-vectors](https://github.com/steering-vectors/steering-vectors), [Representation Engineering](https://github.com/andyzoujm/representation-engineering), and [TransformerLens hooks](https://github.com/TransformerLensOrg/TransformerLens). These libraries are PyTorch-oriented; they do not install a ready-made hook into this MLX hybrid engine.

The installed MLX Qwen3.5-family decoder layer returns the residual output after attention/DeltaNet and MoE/shared-expert updates ([MLX-LM Qwen3.5 implementation](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/qwen3_5.py)). Its routed sparse block computes softmax/top-k and expert scores in the [Qwen3-Next MoE implementation](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/qwen3_next.py). **HybridModel** calls the model through its 40 layers, and its layer list is available at **model.language_model.model.layers**. A temporary pilot wrapper can intercept one selected layer’s call, capture its output during teacher-forced calibration, and return:

\[
h'_{l,t} = h_{l,t} + \alpha d_l
\]

only for generated assistant answer positions \(t\), not the system/user prompt. The hidden size is 2048, so a float32 steering vector is about 8 KiB; 40 vectors are about 320 KiB. Store only per-layer activation sums/means while collecting examples; do not retain full token-by-token activations. Use MLX arrays and a layer wrapper rather than PyTorch hooks. The wrapper must respect prompt-cache positions, batched sequence lengths, and the hybrid model’s layer return shape. This is a temporary inference-only hook; no weight file changes are required.

CAA’s usual steering vectors require **paired preferred/unpreferred answer examples**. We do not currently have a clean held-out-independent set of those pairs. The local diagnosis has categorized failures and the repository has non-held-out prompts/attempt records, but those records must first be audited against the frozen manifest. A small pilot should create 30–50 fresh paired examples across: (i) follow every review note, (ii) avoid unsupported spec additions/omissions, and (iii) preserve explicit API/shape contracts. Pair each prompt/context with a passing answer and a controlled failure. These are labelled contrasts, not class (b). Do not derive the direction from the eight frozen held-out tasks.

## MoE interventions and available traces

The route computation in the MLX Qwen sparse block is conceptually:

1. compute router logits from the normalized hidden state;
2. softmax the logits;
3. select the top 8 experts and normalize their scores;
4. run the selected routed experts and add the shared expert.

A pilot-only wrapper around the router’s gate can add \(b_{\ell,e}\) to logits before softmax/top-8. For calibration, collect unlabeled per-layer expert counts on fresh code and non-code prompts on **this exact Qwen3.6**. A bounded bias can favor experts whose usage is disproportionately coding-oriented; sweep only a small multiplier on development data, keep top-8 fixed, and record read volume/latency as well as quality. This qualifies as (a)+(b)+(d), but is a hypothesis. It can defeat token-conditional routing, increase expert cache/SSD reads, and hurt non-code behavior.

The existing internal route studies are not target-model evidence. Their metrics list 48 layers, 256 experts, top-8, and the only profile file is **engine/hybrid/profiles/Qwen3.5-122B-A10B-8bit.npy**. The target is 40 layers and Qwen3.6-35B-A3B. The trace study supports the general observation that coding can use a distinct expert subset on another model; it cannot tell us which Qwen3.6 experts to bias.

For expert compression, [REAP](https://arxiv.org/abs/2510.13999) and its [Cerebras Research implementation](https://github.com/CerebrasResearch/reap) prune using routing/activation importance without gradient updates. [MC-SMoE](https://arxiv.org/abs/2310.01334) and its [official code](https://github.com/UNITES-Lab/MC-SMoE) align and merge experts before compression. These methods can make models smaller; neither is a justified quality intervention while our streamed 4-bit target already fits. Expert identities are input-dependent, and merging can erase router-controlled specialization. Pruning can reduce disk traffic, but use it only if storage or latency becomes the goal and accept an explicit quality trade-off.

## SAE features

[Qwen-Scope](https://arxiv.org/abs/2605.11887) publishes sparse autoencoders for several Qwen3/Qwen3.5 backbones. The official [Qwen3.5-35B-A3B SAE card](https://huggingface.co/Qwen/SAE-Res-Qwen3.5-35B-A3B-Base-W128K-L0_100) is the closest shape match found: 2048 residual width and layers 1–40, with a 128K feature dictionary. No Qwen3.6-35B-A3B SAE was found in the release. Reusing the Qwen3.5 SAE is class (c)+(d), not training on our examples; optional feature selection could use class (b) calibration. It could support feature inspection and feature-level interventions, but transfer of feature meanings across Qwen3.5→3.6 is unverified. Keep one layer’s SAE in memory at a time and compare it with the much simpler residual-direction pilot.

## Weight editing

[ROME](https://arxiv.org/abs/2202.05262) and [MEMIT](https://arxiv.org/abs/2210.07229) target factual associations in feed-forward layers; their [ROME](https://github.com/kmeng01/rome) and [MEMIT](https://github.com/kmeng01/memit) implementations use a subject/relation/object-style edit set. ROME optimizes an edit value with gradients, so it is not strict class (a); MEMIT’s linear solve can avoid gradients but still requires labelled facts to write. [AlphaEdit](https://arxiv.org/abs/2410.02355) constrains factual edits in a null space; its [implementation](https://github.com/jianghoucheng/AlphaEdit) likewise needs desired fact edits. These are narrowly aimed at factual recall, not a general policy like “follow all review notes”, nor a fix for compiler errors, pointer bounds, or signedness. A local edit could insert one known API fact, but it is not a first-line coding-helper method.

## Inference-time decoding and verification

- **Contrastive Decoding** contrasts an expert model’s logits with an amateur model’s logits ([paper](https://arxiv.org/abs/2210.15097), [code](https://github.com/XiangLi1999/ContrastiveDecoding)). **DoLa** contrasts later-layer and earlier-layer logits ([paper](https://arxiv.org/abs/2309.03883), [code](https://github.com/voidism/DoLa)). Both are class (d); neither has direct evidence for our C/MLX failures. Contrastive Decoding needs another model, while DoLa may change token choice without resolving an API or test contract.
- **Self-consistency** samples multiple reasoning paths and aggregates an answer ([Wang et al.](https://arxiv.org/abs/2203.11171)); class (d). For code, compile/test voting is more meaningful than text majority. Expect approximately N candidate-generation cost.
- **Best-of-N plus execution verification** samples N code candidates and returns a test-passing candidate. This is class (d), and maps directly to our harness. **tools/autofix.py** currently does sequential generate→run→send test failure→repair, not independent best-of-N. A future best-of-N experiment should compare it with sequential repair under equal generation-token and wall-clock budgets.
- **Grammar-constrained decoding** is class (d). It can enforce a fenced block or a syntactic subset, not whether code follows the prompt or uses the right API. Use it only if malformed output is a measured cause; our baseline failure taxonomy is more about semantics and contracts.
- **Speculative decoding** is class (d) and targets speed, not quality. Exact verification preserves the target distribution; it cannot create new coding knowledge. The draft model also competes for unified memory with the target and expert cache.

## Pilot 1 — exact-base coding checkpoint and task-vector merge

**Hypothesis.** The coding post-training already present in KAT or Logics improves first-attempt correctness on our frozen tasks; if both help individually, a same-base merge can retain more useful coding behavior than either alone.

### Required data and availability

- **Available now:** local Qwen3.6 4-bit affine base; local config/index; baseline held-out JSON (2/8 first pass); frozen task manifest and public mini; exact-base metadata for KAT and Logics; public model cards/papers; local C-engine/MLX inference harness.
- **Not downloaded/present locally:** KAT BF16 checkpoint, Logics BF16 checkpoint, immutable source revision identifiers for all checkpoint tensors, and a matched random-delta artifact. They are far larger than 1 GB; none were downloaded in this research task.
- **No data required by the merge formula.** To choose \(\lambda\), however, prepare a fresh development set of roughly 12–20 coding prompts from the non-held-out task families or newly written tasks. Keep the frozen public mini for regression only. Do not use held-out outputs, review prompts, or scores to choose models, layers, merge methods, or \(\lambda\).

### Reproduction gates before touching Qwen3.6

1. **Small published merge reproduction:** use the Model Stock paper’s CLIP ViT-B/32 (151M-parameter) setup and its released same-base fine-tuned checkpoints with the [official model-stock code](https://github.com/naver-ai/model-stock). Reproduce a preselected mean validation metric from the paper’s image-task evaluation using its same task split and checkpoint set. This is the under-1-GB merge-pipeline smoke test; it does not validate MoE support or code quality.
2. **Code-specific merge reproduction:** reproduce the DARE paper’s Llama-2-13B Task Arithmetic + DARE MBPP result (+19.57% as reported by the authors) using the cited MergeLM implementation and same-base public checkpoints. This is a 13B reproduction, smaller than our 35B target but not a claim that it will fit as full BF16 weights in 32 GB. If its storage/RSS requirements cannot be met with chunking, stop the merge branch; still evaluate direct candidate checkpoints later.
3. **Only after both gates:** verify Qwen3.6 parent revisions, tokenizer metadata, tensor names/shapes, and merge software’s handling of Qwen3.6 MoE tensors. Do not infer compatibility from a matching display name alone.

### Arms and controls

1. Base: the local q4 affine checkpoint.
2. Direct checkpoint transfers: Logics-SWE and KAT separately, quantized to the same q4 affine group-size-64 format if their published quantization is incompatible.
3. One candidate merge: TIES or simple task arithmetic over KAT and Logics deltas. Choose the method and \(\lambda\) only on the fresh development set. Use DARE only if delta histograms show the small-update regime.
4. **RANDOM delta control:** for each tensor, generate a seeded random delta with the same shape, per-tensor Frobenius norm, sparsity/mask pattern, global scale, and quantization pipeline as the chosen task-vector merge. Use at least five seeds. This checks whether a merge gain comes from the coding update’s direction rather than simply perturbing weights.
5. Quantization control: base BF16→q4 conversion using the same quantizer, to separate merge effects from requantization effects.

No candidate may use the frozen held-out tasks for selecting model, method, delta coefficients, DARE rate, or quantization settings.

### Evaluation and promotion rule

- Use **tools/ft_eval.py** and **docs/finetune/EVAL.md**. Run held-out first attempt (attempt cap 1), held-out retry cap 3, held-out review-note prompts, and the public mini (HumanEval IDs 5, 7, 58). Keep temperature 0, the frozen system prompt, same task IDs, and the same evaluator revision.
- Run each server checkpoint sequentially using the same **default_model** selector so **tools/ft_eval.py --paired** can pair the JSONs. The evaluator stores a selector string rather than a checkpoint digest; separately record each path, source revision, tokenizer/config hash, quantization config, and output hash in the experiment notes. Do not claim the selector proves which weights ran.
- Compare each checkpoint/merge with base using the existing paired report. It uses 10,000 deterministic paired bootstrap resamples (seed 20261104) for first-pass, pass-at-cap, and attempt score. Report all eight per-task outcomes and the interval. With only eight tasks, the CI will be wide; treat this as a project-specific pilot, not a general coding benchmark.
- Keep public mini as a regression gate: report all three tasks; do not tune against them. Add the full official EvalPlus HumanEval+/MBPP+ suite in a later broader validation if the pilot passes and its data are kept separate from tuning.
- Advance only if a candidate gains at least two net held-out first-pass tasks over 2/8, shows no clear paired-bootstrap evidence of harm, does not regress the public mini, and shows no concentrated loss in review-note mode. If the interval remains broad or crosses zero, call the result uncertain and collect a new task-disjoint evaluation set rather than calling it a win.

## Pilot 2 — residual steering for spec and review-note fidelity

**Hypothesis.** A direction formed from examples that follow all explicit constraints versus examples that drift or ignore review notes can increase selection of the behavior already present in the model. It cannot teach an unknown API or supply missing algorithmic knowledge.

### Required data and availability

- **Available now:** the 40-layer MLX Qwen3.6 model and hybrid forward path; 28 classified prior failure records; non-held-out prompts/attempts; a frozen 8-task held-out suite and 3 public mini tasks.
- **Not ready:** a clean, audited paired contrast set. Build 30–50 fresh pairs (preferred vs controlled failure) across spec fidelity, review-note application, and API-contract preservation. Audit every source task against **tools/ft_eval_manifest.json**; exclude all held-out first-attempt and review prompts, outputs, and derivative paraphrases. The pair labels are necessary for CAA, so this is not class (b) under the no-label definition.
- No gradient updates or optimizer. Calibration requires teacher-forced forward passes only, with streaming per-layer means.

### Reproduction gates before touching Qwen3.6

1. Use the published CAA code to reproduce its Llama 2 7B sycophancy effect at the paper’s layer 13 and multipliers ±2 on its published behavior set. Compare directional change with the paper’s result. The weights exceed the 1 GB research-download limit, so nothing was downloaded now; this is a future pilot prerequisite.
2. Implement the same activation capture/addition on a small public causal model in MLX and confirm that the wrapped layer output changes by exactly the requested vector only at selected answer positions. This verifies the MLX hook and prompt-cache mask, not a coding-quality gain.
3. Only then instrument the local hybrid 35B model.

### Direction construction, controls, and evaluation

1. Split the fresh pairs into direction-building and development partitions by task, not by completion. For each pair and each of 40 block outputs, average activations over assistant answer tokens and compute preferred-minus-unpreferred residual means. Accumulate sums online; do not retain full sequences.
2. Normalize candidate directions and sweep layer/strength on development prompts only. Use a small strength grid scaled by that layer’s residual RMS; select one layer/strength and freeze it before held-out evaluation. Apply \(h' = h + \alpha d\) after the chosen decoder block only on generated assistant positions.
3. **RANDOM direction control:** at the selected layer, compare against at least five seeded random 2048-dimensional directions with the same L2 norm/RMS and exactly the same \(\alpha\), hook, masks, and inference settings. Also report an unsteered base. Random directions must not be chosen after inspecting held-out results.
4. Run the same four evaluator modes as Pilot 1: held-out cap 1, cap 3, review-note mode, and public mini. Add paired bootstrap intervals and per-task outcomes. Keep the task IDs and temperature identical. For activation results, report differences against both base and the random-direction distribution.
5. Require the same promotion rule as Pilot 1: at least two net held-out first-pass tasks above baseline, no clear evidence of harm in the paired interval, no public-mini regression, and improvement concentrated in the intended spec/review categories rather than a coincidental unrelated pass. Treat any interval spanning both meaningful harm and benefit as inconclusive.

### Cost estimate and implementation risk

The direction storage is under 0.4 MiB for all 40 layers in FP32. The expensive part is the forward-pass collection and generation of the labelled pairs; it needs no backward pass and no ~27 GB training workspace. During one hook call, retain only the current layer output and running activation sums. Stop the inference server while the capture process owns the model, then restart it with the steering wrapper. Main risks are prompt-cache position errors, applying the vector to user/system prompt tokens by accident, and selecting a layer/scale on the held-out set.

## What will not work for us

- **Local full gradient fine-tuning:** it violates the stated ~27 GB GPU-memory constraint and is outside this research task.
- **Abliterating or pruning experts to improve code quality:** those are refusal/compression interventions; current evidence does not connect them to our compile/spec/API failures, and pruning trades away quality.
- **Copying 122B expert IDs into the 35B router:** the profile has 48 layers versus our 40; expert IDs and layer patterns do not transfer.
- **Using ROME/MEMIT/AlphaEdit as a general “follow the spec” patch:** they edit facts, not broad instruction-following policy.
- **Assuming a Qwen3.5 SAE feature means the same thing in Qwen3.6:** matching width and layer count is not feature-level compatibility.
- **Using grammar constraints to fix C semantics:** syntax constraints do not establish correct bounds, API contracts, or signedness.
- **Using speculative decoding as a quality method:** it can reduce latency, not change the target model’s capability.
- **Merging directly in MLX q4:** the packed affine weights are not the same-base floating-point deltas required by task arithmetic/TIES/DARE; dequantize or use the original BF16 sources, merge, then requantize.

## Research limits

This is a source review, not an executed pilot. No remote model files, tokenizer files, or benchmark datasets were downloaded. The HF model search was limited to name/tag queries and model cards; weights and every community merge were not audited. Before adopting a checkpoint, check its immutable base revision, license, tensor mapping, tokenizer files, and quantization behavior. The published benchmark numbers above come from their authors’ evaluation setups and are not directly comparable to our eight-task frozen suite.
