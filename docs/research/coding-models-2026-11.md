# Open-weight coding models for this Mac

Hub and leaderboard snapshot checked as of [2026-11-04](https://huggingface.co/api/models?author=mlx-community&search=coder&sort=lastModified&direction=-1&limit=100). This is a model-selection note for the stated M1 Max workload. Checkpoint sizes are sums of Hub-listed safetensors files in decimal GB; metadata and configs were read, and no model weights were downloaded.

## Selection criteria

- Keep models released or updated during [2026](https://huggingface.co/api/models?author=mlx-community&search=coder&sort=lastModified&direction=-1&limit=100) in scope. Include the specifically requested GPT-OSS-120B Q4 checkpoint as an out-of-window control because its MLX revision is still useful for comparison.
- Prefer exact-model maintainer-run coding results. Keep model-author reports separate and never use them as independent pass probabilities.
- Treat a missing local adapter or layer path as integration work. In particular, [Qwen3-Coder-Next is eligible](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/qwen3_next.py): the reported <code>language_model.model.layers</code> versus <code>model.layers</code> path change is a small hybrid-loader adaptation, not a model rejection.
- Reject only for the stated hard limits: no upstream <code>mlx-lm</code> model support, selected checkpoint above the supplied roughly 100 GB free-disk limit, or dense weights plus runtime/KV exceeding the supplied 12–16 GB model-memory budget. These are machine constraints from the brief. A model that needs a new expert adapter remains a candidate if upstream <code>mlx-lm</code> supports its architecture.
- Rank by expected wall-clock time to an accepted task. Use external coding scores as screening evidence; use local first-try passes, retries, and time per task for the final decision.

## Speed model and assumptions

For a routed MoE, I use the requested estimate:

> <code>active expert bytes/token = sparse layers × top_k × [3 SwiGLU projections](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/switch_layers.py) × hidden_size × moe_intermediate_size × bits/8</code>

The SSD-only ceiling is [6.5 GB/s](#speed-model-and-assumptions) ÷ active expert bytes/token; shared experts, attention, router and metadata stay in RAM. The [150–200 GB/s](#speed-model-and-assumptions) dense-memory estimate gives dense decode ceiling: bandwidth ÷ actual checkpoint weight bytes. These bandwidth figures are supplied machine facts. They are ceilings, not benchmark predictions.

For the current Qwen MoE path, I calibrate extrapolations against the local [Qwen3.6-35B-A3B 4-bit reference: 0.503 GB/token and 6.2–7.4 tok/s](../../docs/MLX_ENGINE.md), and the [Qwen3.5-122B-A10B 8-bit reference](../../docs/MLX_ENGINE.md): the requested active-expert formula gives 3.624 GB/token, while the local measurement is about [3.8 GB/token at 1.2–1.5 tok/s](../../README.md). This difference is expected because the formula excludes shared experts, attention, and other reads. For other MoE families, the table reports the SSD ceiling only until measured. Dense bytes/token uses the actual MLX file size when that width exists; for missing widths it uses total parameters × nominal bits/8 as a lower-bound estimate. An em dash size means no matching conversion appeared in the linked Hub search.

## Expected cost per accepted task

The quantity to optimize is:

> mean end-to-end seconds per attempt × mean attempts until acceptance

A generation-only proxy for equal output length is output tokens ÷ (first-try pass probability × tok/s). Benchmark pass rate is only a temporary proxy for local pass probability; task mix and harness differ.

**The final expected-cost rank is not identifiable from public evidence for the shortlist:** none has an exact independent success probability on the local brief set. For test scheduling, an equal-quality pass-probability sensitivity ranks the shortlist by speed:

- **Lowest latency cost if quality clears its break-even:** Gemma-4-12B-Coder, about [16.7–22.3 tok/s](#speed-model-and-assumptions). It costs less than KAT at equal output length if its first-try pass probability is at least [0.28–0.44](#expected-cost-per-accepted-task) times KAT's.
- **Next:** KAT-Coder-V2.5-Dev, about [6.2–7.4 tok/s](#speed-model-and-assumptions), with a Qwen-family streaming path already present. It costs less than Qwen3-Coder-Next if KAT's first-try probability is at least [0.56–0.79](#expected-cost-per-accepted-task) times Qwen3-Coder-Next's.
- **Highest latency cost, highest specialist upside to validate:** Qwen3-Coder-Next, about [4.13–4.93 tok/s](#speed-model-and-assumptions). To beat KAT on generation time, it needs [1.26–1.79×](#expected-cost-per-accepted-task) KAT's first-try probability.

Those are break-even conditions, not predictions. The shortlisted models' public scores are vendor/in-house or absent, so they do not supply independent probabilities. As an external calibration only, Devstral's [56.40%](https://www.swebench.com/) Verified result and [9.93–13.24 tok/s](#speed-model-and-assumptions) dense ceiling imply [0.134–0.179 seconds per generated output token](#expected-cost-per-accepted-task) if that benchmark rate transferred unchanged. Its Q4 weights use almost the whole model-memory allowance, so it is not in the robust shortlist. GPT-OSS-120B's [16.20%](https://scale.com/leaderboard/swe_bench_pro) Pro rate against a [3.63 tok/s](#speed-model-and-assumptions) SSD ceiling is at least [1.70 seconds per output token](#expected-cost-per-accepted-task), before harness/runtime overhead; that cost signal and required MXFP4 integration make it a poor first local test.

## Open questions

- Exact official training cutoffs were not available for the candidate model cards/reports checked. LiveCodeBench's displayed window ends at [2025-05-01](https://livecodebench.github.io/leaderboard.html); without cutoffs, its contamination status cannot be established for these models.
- The public independent tables provide no exact-model score for most candidates. For Qwen3-Coder-Next and KAT, their model-card scores are not independent replications. GPT-OSS-120B has multiple independent scores, but they use different tasks and harnesses.
- KAT's OptiQ tensor quantization layout needs a local compatibility check against the affine expert reader. GPT-OSS MXFP4 needs a format-aware MLX expert path. Neither is rejected for this integration work.
- Gemma's Q4 OptiQ file is mixed precision. The Q6/Q8 speed numbers are nominal lower-bound estimates, not available checkpoints.
- The Kestrel coder entry is an empty Hub repository at this snapshot, with no config or safetensors.
- Dense models' real decode rate depends on the loaded weight bytes, context/KV length, and memory pressure; bandwidth estimates do not include that overhead.

## How we will verify

Replay the same [15 delegated tasks](../delegation-log.md) from [docs/briefs/01-15](../briefs), using the existing automatic tests under <code>engine/tests</code> and <code>engine/hybrid/test_*.py</code>. Keep prompts, tool permissions, timeouts, repository state, and context limits fixed across models. For each task and candidate, record:

- first-try pass/fail against the existing automatic tests;
- total attempts and corrections until acceptance;
- wall-clock seconds to acceptance, including generation and test runs;
- generated tokens and decode tok/s.

Rank the models by first-try pass rate, mean attempts, and mean/median end-to-end seconds per accepted task. Review spec drift, ignored review notes, and buffer handling separately. Public leaderboards are screening evidence; the replay is the decision.
