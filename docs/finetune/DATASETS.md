# Public dataset screen for the local coding helper

**Decision:** do not add a large public corpus to the first pilot. Use the project's executable seeds, eligible accepted task logs, and a small set of new tasks with independently checked tests. Public datasets are useful sources of candidate prompts and preference signals, but most either have uncertain row-level licensing, no execution labels, weak coverage of C99/numerical kernels, or a benchmark leakage risk. The proposed pilot mix is at the end.

## Scope and evidence standard

The user's requested research was routed through the CamoFox MCP browser with `userId=moe-research`. No dataset shard or paper PDF was downloaded. The Hugging Face API query for `KodCode` exposed the original KodCode card metadata and the 2026 `F-A-I-L/kodcode-verified-python-235k` card text. The entries below include HF source links or source-discovery links and primary papers/repos where identifiable; all fields described as unknown or requiring verification remain unconfirmed. This is a screening memo, not legal clearance or a claim that all test suites were independently rerun here.

For HF card checks, use both the dataset page and the raw API response, for example:


Pin the dataset commit SHA and inspect the exact file/row fields before conversion. Dataset-level license tags do not necessarily clear the underlying code, problem statements, packages, or repository license. A reported “tested” label is not equivalent to independent, hidden tests for the specification.

### Dataset-specific held-out leakage screen

`tools/ft_eval_manifest.json` identifies these held-out target files: `qmat.c`, `ops.c`, `gdn.c`, `qmat_row.c`, `qgroup.c`, `expert_cache.py`, `predictive.py`, and `pinned.py`. Target symbols include `qmat_matvec`, `qmat_row`, `qgroup_dot`, `op_rmsnorm`, `op_silu_mul`, `op_sigmoid`, `op_softmax`, `op_topk`, `op_rope`, `gdn_conv_step`, `gdn_l2norm`, `gdn_gates`, `gdn_recurrent_step`, `ExpertCache`, `PredictivePrefetcher`, and `select_pinned`.

Before accepting any external row, exact-match scan prompts, code, comments, function names, and test fixtures against those names and task descriptions. Also manually screen semantic neighbors: unsigned 4/8-bit unpacking and quantized matvec; Gated DeltaNet recurrence; RMSNorm/SiLU/softmax/rotary embeddings; stable top-k ties; MoE expert caching, sorted row reads, prefetch cleanup, and byte-budget pinning. Exact name matches are likely low for general datasets, but public contest/corpus data can contain the same algorithm under different names. No card's benchmark decontamination claim proves non-overlap with this project.

## Recommended training mix

**Default first run: zero external HF rows.** The 19 GB 4-bit base and tiny, task-specific verified corpus make a public bulk download and broad mix a poor fit. This is the concrete, auditable pilot mix (all counts refer to the train split):

- **200 teacher-created C99/Python tasks** from `tools/ft_build_dataset.py --teacher-count 250`: 50 each across C99 kernel, Python stdlib, NumPy, and skeleton-fill categories; 200 train and 50 validation by the builder's fixed every-fifth holdout. Execute with the provided tests, then independently inspect/augment each test suite before calling the row verified. Reject vague specs, unbounded allocation, external dependencies, missing edge tests, duplicates, held-out keywords/symbols, and any test suite that can accept an obviously wrong implementation.
- **22/28 checked-in seeds** for training: 10 C99/skeleton kernels, 8 Python stdlib/skeleton tasks, and 4 NumPy tasks; keep 6 seeds in validation. The checked-in C tests compile with `-std=c99 -Wall -Wextra -Werror`; Python/NumPy assertions run locally.
- **6 natural accepted train tasks** from the builder's train IDs (`gdn-layer`, `attn-layer`, `moe-layer`, `qchat`, `fetch-experts`, `read-sorted`), plus **3 review-following corrections** from those train tasks. Do not promote validation-only `model-forward`/`expert-reader`; never use held-out IDs.
- Current total after 250 accepted teacher tasks: **231 train rows** (200 teacher + 22 seeds + 6 natural + 3 review) and **60 validation rows** (50 teacher + 6 seeds + 2 natural + 2 review). The current builder reports 31/10 before teacher generation.
- **Preference data:** retain the existing three train-only pass/fail pairs in `preferences.jsonl`, but do not preference-tune on three pairs. Collect additional real test-failed/test-passing pairs only from train-eligible tasks; require at least 50 distinct prompt/pair examples and no held-out IDs before reconsidering ORPO/DPO.

**Conditional public add-on:** if non-commercial use is acceptable, inspect at most 128 rows from `KodCode-Verified Python` as a Python-only candidate, pin its HF revision, verify its `non-commercial` terms, drop near-duplicates/benchmark fingerprints, and run our own Python tests. Do not combine it with original KodCode rows. For commercially usable data, first confirm the pinned card/license for a source such as OpenCoder/Magicoder, then retain at most 64 task prompts and independently run tests; the first pilot should still remain local-data-only unless these rows beat the teacher/seed mix on validation without shifting the C/Python distribution.

No external dataset was downloaded in this review. All proposed counts are well below the 1 GB research limit.
